# Детектор автоматизированного трафика

## Идея решения

Для каждой `cookie_id` нужно получить `score` от 0 до 1: чем выше значение, тем вероятнее, что cookie относится к автоматизированному трафику.

Основная метрика:

\[
P@R_{\ge 0.7} = \max_{t: Recall(t) \ge 0.7} Precision(t)
\]

Порог отправлять не нужно: проверяющая система перебирает его самостоятельно. Поэтому модель в первую очередь должна хорошо ранжировать cookie.

---

## Данные и защита от утечки

В исходных файлах:

- `train.csv` — 11 091 cookie;
- `test.csv` — 4 909 cookie;
- `events.csv.gz` — 328 905 событий;
- доля положительного класса в train — около 8.1%.

Train расположен по времени раньше test: обучающие окна идут с 6 по 19 апреля 2026 года, тестовые — с 20 по 26 апреля.

Ключевое ограничение задачи — использовать можно только события внутри индивидуального окна наблюдения:

```python
window_start_ts <= event_ts < window_end_ts
```

В исходном журнале есть события позже `window_end_ts`. Они отбрасываются до построения любых признаков. Это особенно важно для `captcha_shown`: такие события находятся за допустимым окном и не используются.

## Признаки

Для каждой cookie журнал событий агрегируется в одну строку. В итоговой таблице 342 признака.

Основные группы:

- объём и плотность активности;
- интервалы между соседними событиями;
- количество и доли разных типов событий;
- переходы между типами событий;
- количество уникальных объявлений, категорий, локаций и запросов;
- глубина просмотра поисковой выдачи;
- User-Agent и платформа;
- координаты указателя и параметры перемещения;
- возраст cookie;
- дубли и всплески событий.

Самыми полезными оказались поведенческие признаки: интервалы между событиями, плотность активности, поисковая глубина, разнообразие локаций и объявлений, а также признаки указателя.

## Почему валидация сделана по времени

Случайный `train_test_split` здесь плохо повторяет реальный сценарий: скрытый test расположен позже train.

Первоначально использовался один последний временной holdout. На нём метрика получалась заметно выше, чем на соседних временных срезах. Это показало, что одной точки проверки недостаточно: `P@R>=0.70` чувствительна к нескольким объектам около рабочего порога и к временному дрейфу.

В текущей версии используется rolling temporal validation на двух последних отрезках:

```text
fold 1: train < 2026-04-16, valid = 2026-04-16 ... 2026-04-18
fold 2: train < 2026-04-17, valid = 2026-04-17 ... 2026-04-19
```

Запуск:

```bash
python solution/train.py --data-root . --validate
```

В `validation_report.csv` сохраняются результаты для каждого временного фолда.

## Финальная модель

Вместо смеси CatBoost и XGBoost используется ансамбль двух CatBoost-моделей.

Первая модель обучается на всём train с одинаковым весом объектов.

Вторая получает экспоненциальные веса по давности наблюдения:

```text
half-life = 3 дня
```

То есть более свежие дни имеют больший вес. Это не использует target и нужно только для того, чтобы немного уменьшить влияние старых паттернов перед прогнозом на будущий период.

Финальный score:

```python
score = 0.70 * rank(base_catboost) + 0.30 * rank(recency_catboost)
```

Смешиваются ранги, а не вероятности, потому что итоговая метрика зависит прежде всего от порядка объектов.

Параметры основной модели:

```python
iterations=780
depth=6
learning_rate=0.045
l2_leaf_reg=7
random_strength=0.5
random_seed=42
```

Параметры recency-модели немного отличаются по регуляризации и seed, чтобы модели не были полностью одинаковыми.

## Запуск

Установка зависимостей:

```bash
pip install -r solution/requirements.txt
```

Финальное обучение:

```bash
python solution/train.py --data-root . --output solution/submission.csv
```

С rolling temporal validation:

```bash
python solution/train.py --data-root . --validate --output solution/submission.csv
```

Только основная модель без recency-ансамбля:

```bash
python solution/train.py --data-root . --base-only --output solution/submission_base.csv
```

Перед сохранением проверяются:

- число строк;
- уникальность `cookie_id`;
- отсутствие `NaN`;
- диапазон `score` от 0 до 1;
- соответствие cookie из `test.csv`.

## Ограничения

Главная проблема задачи — временной дрейф. Положительный класс описывает известные сервисы автоматизированного сбора данных, поэтому их поведение и технические признаки могут меняться со временем.

По этой причине я не стал опираться на один последний holdout или сильно подбирать параметры под одну дату. Основной упор сделан на поведенческие признаки и проверку на нескольких последовательных временных срезах.
